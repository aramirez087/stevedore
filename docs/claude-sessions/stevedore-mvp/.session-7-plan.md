## Key Design Decisions (already codified — do not revisit)

### 1. Observation via continuation dictionary, not NotificationCenter
The session spec says "Backed by `NotificationCenter` under the hood" but the
implementation uses a `[String: [UUID: AsyncStream<Data>.Continuation]]`
dictionary instead. This is strictly better:
- No string-based `Notification.Name` coupling.
- No cross-process notification leakage.
- Cleaner actor-isolation model.
Record in the handoff as a deliberate divergence from the spec.

### 2. UserDefaults stores JSON-encoded `Data` uniformly
Every `Setting<Value>` — Bool, String, Double — is JSON-encoded to `Data` and
stored in UserDefaults rather than using type-specific setters
(`setBool`, `setDouble`, etc.). This makes the encode/decode path isomorphic to
`InMemorySettingsStore`, prevents type-mismatch surprises, and avoids a
dispatch matrix. Cost: slightly larger UserDefaults entries.

### 3. Atomic write via tmp + replaceItem/moveItem
`JSONFileStore.write` serializes to a `.json.tmp` sibling, then:
- If the destination exists: `FileManager.replaceItem(at:withItemAt:)` — an
  atomic rename on APFS/HFS+.
- If the destination is absent: `FileManager.moveItem(at:to:)`.
The stale `.tmp` is deleted on init so a mid-write crash leaves the last good
`.json` intact and returns defaults on next read.

### 4. Repository cache-on-first-access
Each repository holds an optional `cache: [T]?`. The first `all()` or
`loaded()` call reads from the JSONFileStore and caches. Subsequent reads are
`O(1)` in-memory. The cache is updated on every `save()` before writing to
disk; this prevents a re-read race window.

### 5. allKeys literal enforces catalog completeness
`Settings.allKeys` is a manually maintained literal; `SettingsCatalogTests`
asserts `count == 15` and uniqueness. Adding a setting without updating `allKeys`
fails the test. Adding to `allKeys` without declaring the setting fails to
compile.

## Risks and Mitigations

### Risk 1: swiftformat violations in existing files
Prior sessions generated the source; swiftformat may flag style issues.

**Mitigation:** Run `swiftformat --lint Sources/Services/Settings Tests/ServicesTests/SettingsTests`
early. Fix any violation before touching anything else so the baseline is clean.

Common swiftformat issues to look for:
- Multi-line `throw` expression split across lines (Session 01 established `--commas always`).
- Trailing newline on `JSONFileStore.swift` (anatomy.md shows line 145 is blank — verify it ends at exactly one trailing newline).

### Risk 2: swiftlint strict violations
`swiftlint --strict --path Sources/Services/Settings` may flag:
- `private var continuations` property complexity (deeply nested generic type).
- `force_cast` / `force_try` — none expected.
- Cyclomatic complexity in `JSONFileStore.read`.

**Mitigation:** Run lint immediately after format. Each violation has a unique
fix strategy:
- Nested generic types: type alias to a named private typealias.
- Complexity: extract sub-function.

### Risk 3: observe() double-emit
Between `registerObserver` (which adds the continuation to the bucket) and
reading the initial snapshot, a concurrent write can be buffered AND appear in
the snapshot. The subscriber sees the updated value twice.

**Impact:** benign — SwiftUI de-bounces identical re-renders. No data corruption.
**Mitigation:** Document in the handoff. Do not "fix" this without a failing
test, as any fix introduces its own locking surface.

### Risk 4: SettingsCatalogTests count is hardcoded at 15
`testAllKeysCoverEveryStaticSetting()` asserts `count == 15`. If a new setting
is added during Session 7 or later without updating the test, it will fail.

**Mitigation:** The hardcoded count is by design — it enforces the catalog stays
in sync. Do not change the approach; simply make sure count == actual declared
settings. No new settings need to be added for Session 7's scope.

### Risk 5: JSONFileStore directory not constructed by the repository
`JSONFileStore.init(directory:filename:schemaVersion:)` takes a caller-supplied
`URL`. Repositories receive a pre-constructed store. Nothing in the Settings
module creates the Application Support path — that's the application's
responsibility at startup. This is correct but must be documented so future
UI sessions know how to wire it up.

**Mitigation:** Note in the handoff under "Application startup wiring."

## Application Startup Wiring (for Session 24 / Session 26)

When the Settings UI or main window shell wires up the repositories, the
pattern is:

```swift
// NOT in ServicesSettings — caller's responsibility
let appSupport = FileManager.default
    .urls(for: .applicationSupportDirectory, in: .userDomainMask)[0]
    .appendingPathComponent("Stevedore")

let bookmarksStore = try JSONFileStore(directory: appSupport, filename: "bookmarks")
let bookmarksRepo  = BookmarksRepository(store: bookmarksStore)

let workspacesStore = try JSONFileStore(directory: appSupport, filename: "workspaces")
let workspacesRepo  = WorkspacesRepository(store: workspacesStore)

let recentStore = try JSONFileStore(directory: appSupport, filename: "recent-connections")
let recentRepo  = RecentConnectionsRepository(store: recentStore)

let settingsStore = UserDefaultsSettingsStore()
```

Note that `JSONFileStore.init` throws (creates directory if needed); the caller
must propagate or handle the error.
