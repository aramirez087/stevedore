## Key Type Signatures

### SettingBinding

```swift
import Core
import Observation
import ServicesSettings
import SwiftUI

/// Bridges a `Setting<T>` to a SwiftUI `Binding<T>` by subscribing to the
/// store's `AsyncStream` and writing back immediately on set.
///
/// Must be created on `@MainActor` and injected into views as a `@State` or
/// `@Bindable` property.
@Observable
@MainActor
public final class SettingBinding<T: Codable & Sendable & Equatable> {
    public private(set) var value: T
    private let setting: Setting<T>
    private let store: any SettingsStore
    private var observationTask: Task<Void, Never>?

    public init(setting: Setting<T>, store: any SettingsStore) {
        self.setting = setting
        self.store = store
        self.value = setting.defaultValue
    }

    /// Starts stream subscription. Call from `.task` modifier or `onAppear`.
    public func start() {
        self.observationTask?.cancel()
        self.observationTask = Task { [weak self] in
            guard let self else { return }
            for await v in self.store.observe(self.setting) {
                guard !Task.isCancelled else { break }
                self.value = v
            }
        }
    }

    /// Cancels stream subscription. Call from `onDisappear` or deinit.
    public func stop() {
        self.observationTask?.cancel()
        self.observationTask = nil
    }

    /// SwiftUI `Binding<T>` that reads `value` and writes through the store.
    public var binding: Binding<T> {
        Binding(
            get: { self.value },
            set: { [weak self] newValue in
                guard let self else { return }
                self.value = newValue
                Task { await self.store.set(newValue, for: self.setting) }
            }
        )
    }
}
```

**Concurrency rationale:** `@Observable` + `@MainActor` is Swift 6-safe because
all mutations of `value` happen on `MainActor`. The `store` is `any SettingsStore`
(which is `Sendable`), so it can be held on `MainActor` without isolation warnings.
`Task { await store.set(...) }` inherits `MainActor` context and then suspends to
the store's actor — this is the correct pattern; do NOT use `nonisolated` here.

func testEmitsDefaultOnSubscribeWhenStoreIsEmpty() async {
    let store = InMemorySettingsStore()
    let binding = SettingBinding(setting: Settings.theme, store: store)

    // Allow one async tick for the stream task to deliver the initial value

**Note on `Task.yield()`:** A single `yield` may not be enough for multi-hop async
delivery. Use a polling helper with a short timeout:

```swift
func waitForValue<T: Equatable>(
    _ binding: SettingBinding<T>,
    equals expected: T,
    timeout: Duration = .milliseconds(500)
) async {
    let deadline = ContinuousClock.now + timeout
    while binding.value != expected, ContinuousClock.now < deadline {
        await Task.yield()
    }
}
```

## Key Design Decisions and Rationale

### SettingBinding as @Observable class, not @State struct

`Setting<T>` bridging requires a mutable `Task` reference and a backing `value`
property that SwiftUI can observe. A struct cannot hold a cancellable task while
also being `@State`. Using `@Observable final class` gives:
- Automatic SwiftUI invalidation when `value` changes (via `@Observable` macro).
- A `Task` the class owns for its lifetime.
- Clean `start()`/`stop()` lifecycle hooks matching SwiftUI's `.task`/`onDisappear`.

Using `@MainActor` on the class ensures all `value` mutations happen on the main
thread — required for SwiftUI `@Observable` properties.

### No environment injection for the store

The `SettingsScene` takes `any SettingsStore` as a direct `init` parameter rather
than reading from `@Environment`. Rationale: Settings windows are singletons in
macOS apps, constructed once in the app delegate / composition root. Environment
injection would require the caller to insert a custom `EnvironmentValues` key in
every preview and test host. Direct injection is simpler and more testable.

### Immediate write on change (no Apply/Cancel buttons)

macOS Settings panels (System Preferences style) write immediately. The `binding`
property fires `store.set` in a fire-and-forget `Task` with no debounce. For the
settings in scope (strings, bools, ints), writes are idempotent and cheap.

### Form container for each tab

`SwiftUI.Form` on macOS renders as a sidebar-style grouped list, which matches the
macOS Settings aesthetic. DesignSystem components (`SDTextField`) are used for text
fields; native `Picker`, `Toggle`, and `Stepper` are used for their respective
control types — these are not wrapped in DesignSystem (out of scope for S08).

### Setting<Int> for logRingBufferSize and transferConcurrencyCap

The new `logRingBufferSize` and `transferConcurrencyCap` settings use `Setting<Int>`
(not `Setting<Double>`). `Stepper` binds directly to `Binding<Int>`. Avoid
`Setting<Double>` here — using the wrong type would silently store/read incorrect
values from the JSON store.

### Test directory naming

The existing smoke test lives in `Tests/UITests/SettingsUI/` (not
`Tests/UITests/SettingsUITests/`). All new tests must go into
`Tests/UITests/SettingsUITests/` (a new subdirectory). This matches the test filter
specified in the quality gates: `--filter SettingsUITests`. The UITests target uses
a single path (`Tests/UITests`) and discovers all subdirectories recursively, so no
`Package.swift` change is needed for the new subdirectory.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| `@Observable` macro requires `import Observation` — missing import causes "cannot find type" errors | Always `import Observation` explicitly in `SettingBinding.swift` |
| Swift 6: `Task { await store.set(...) }` inside a `Binding.set` closure crosses actor boundary | `Binding.set` closure is `@MainActor` because `SettingBinding` is `@MainActor`; `Task { ... }` inherits that isolation, then suspends to the store actor — legal in Swift 6 |
| `any SettingsStore` held on `@MainActor` class triggers `Sendable` warning | `SettingsStore: Sendable` (confirmed in `Sources/Core/Protocols/SettingsStore.swift`); `any SettingsStore` is `Sendable`; no warning |
| `SettingsCatalogTests` unique-key assertion will fail if `allKeys` is not updated | Explicitly update `allKeys` after adding each new `Setting` constant |
| New `Setting<Int>` constants: the catalog tests check key uniqueness but not type correctness | Manual review: confirm `logRingBufferSize` and `transferConcurrencyCap` use `Int`, not `Double` |
| `Stepper(value:in:step:)` requires `Binding<Int>` but `SettingBinding.binding` returns `Binding<T>` | No issue — `SettingBinding<Int>.binding` returns `Binding<Int>` via generic specialisation |
| SwiftFormat 0.59 bug: paths must come before `--lint` | Use `swiftformat Sources/UI/SettingsUI Tests/UITests/SettingsUITests --lint` (paths first) |
| SwiftLint `trailing_comma: mandatory_comma: true` — trailing comma required in all multi-line collections | Add trailing commas to all multi-line array/dict literals; verify before commit |
| `NSHostingView` in tests requires macOS target — already satisfied (macOS 14+) | No action needed |
| `Task.yield()` may not be sufficient for multi-hop async in `SettingBindingTests` | Use a polling helper with a `ContinuousClock` deadline (see test outline above) |
| macOS `Settings` scene integration: `SettingsScene` must be used as a child of `SwiftUI.Settings { }` scene — it is a `View`, not a `Scene` itself | `SettingsScene` is a `View` (the content of the `Settings` scene), not a `Scene`. The actual `SwiftUI.Settings` scene wrapper lives in the app target. Name clearly to avoid confusion. |
