## 2. Design decisions and rationale

### 2.1 Visibility: promote `FileBrowserView` to `internal`
The view is `private struct FileBrowserView` at
`PaneHost.swift:176`. Tests in the `MainWindowTests` target use
`@testable import MainWindow`, which exposes `internal` symbols but
not `private`. Promoting to `internal` is a one-keyword diff and
allows direct construction in T1–T5. Rejected alternative: extracting
a `FileBrowserModel` view-model — more code, no real testability win
because the gesture closures are trivial.

### 2.2 Trash routing: **direct provider call** for S02 MVP
The S01 handoff recommended closure injection
(`PaneHost` → `FileBrowserView`) so the operation flows through
`MainWindowModel.operationQueue`. That is the architecturally clean
choice but requires touching `PaneHost.init`, `MainWindowView`, and
their call sites — none of which are mandated by the S02 prompt's
exit criteria.

The S02 prompt task 2 says explicitly:
> **Move to Trash** — call `session.provider` trash operation if
> available; otherwise show disabled.

I will follow the prompt literally:

```swift
Button("Move to Trash") {
    let descriptor = OperationDescriptor(kind: .trash, sources: [item.path])
    Task { _ = try? await self.session.provider.execute(descriptor, progress: nil) }
}
.disabled(item.path.scheme != .local)
```

The transfers panel will not show this op. I'll record this trade-off
in the handoff under "Open issues" so a future session can plumb
through `FileOperationQueue` if product wants progress UI.

### 2.3 Gesture order: double-tap declared **before** single-tap
Documented gotcha #1 in S01 handoff. Reversing this order silently
breaks double-tap. The modifier chain on the row `HStack` will be:

```swift
.background(self.rowBackground(for: item))
.contentShape(Rectangle())
.onTapGesture(count: 2) { self.handleDoubleTap(item) }
.onTapGesture(count: 1) { self.selectedItemPath = item.path }
.contextMenu { self.contextMenu(for: item) }
```

`.contextMenu` is attached last; it listens on right-click and does
not conflict with the tap recognizers.

### 2.4 Selection state lives in the view, not on `PaneSession`
`@State private var selectedItemPath: FilePath?` — pane-local,
auto-clears on `onChange(of: self.session.currentPath)`. Matches S01
gotcha #4. Do **not** introduce `List(selection:)` (gotcha #3) — keep
the existing `List(self.items, id: \.path)` form.

### 2.5 Selection highlight via `.background`
Per S01 sketch and `Sources/UI/DesignSystem/Components/SDListRow.swift:29`,
the existing convention is `theme.colors.accent.opacity(0.15)`. Use a
helper:

```swift
private func rowBackground(for item: FileItem) -> Color {
    self.selectedItemPath == item.path
        ? self.theme.colors.accent.opacity(0.15)
        : Color.clear
}
```

### 2.6 Context menu items (per S02 prompt task 2)
Minimum required: **Open**, **Move to Trash**, **Reveal in Finder**.
Per task 4, placeholders must be visible-but-disabled, not omitted —
that means a non-actionable item (e.g., "Open" on a non-local file)
shows as a greyed-out menu entry rather than disappearing.

| # | Label | Action | Disabled when |
|---|---|---|---|
| 1 | **Open** | directory → `session.navigate(to: item.path)`; file (local) → `NSWorkspace.shared.open(URL(fileURLWithPath: item.path.posixString))` | `item.kind != .directory && item.path.scheme != .local` |
| 2 | **Reveal in Finder** | `NSWorkspace.shared.activateFileViewerSelecting([URL(fileURLWithPath: item.path.posixString)])` | `item.path.scheme != .local` |
| 3 | **Move to Trash** | `Task { _ = try? await session.provider.execute(.init(kind: .trash, sources: [item.path]), progress: nil) }` | `item.path.scheme != .local` |

`Divider()` between Reveal and Trash for visual separation
(matches macOS conventions). Drop placeholders #6/#7 from the S01
spec — they were optional and add no user value.

### 2.7 Double-tap on a non-directory: open with `NSWorkspace`
S02 prompt task 6 says "navigate into directory or open file with
`NSWorkspace`". Local files only; remote files are a no-op (we have
no opener). Wrap in `if item.path.scheme == .local`.

### 2.8 AppKit import already present?
Currently `PaneHost.swift` imports `Core, DesignSystem, Foundation,
SwiftUI, UIMenus, UIToolbar`. `NSWorkspace` lives in `AppKit`. Need
to add `import AppKit` at the top.

| # | Risk | Likelihood | Mitigation |

| R3 | SwiftFormat reorders the two `.onTapGesture` calls or rewrites the trailing-closure form. | low | Run `swiftformat --lint` in gate 3 before declaring done. If it complains, restructure as separate statements rather than chained modifiers. |
| R4 | SwiftLint `closure_body_length` or `function_body_length` triggers on the `body` getter. | low | Extract `contextMenu(for:)` and `handleDoubleTap(_:)` into private methods (already planned). |
| R5 | `selectedItemPath` survives across tab switches (S2 doesn't clear it). | low | `onChange(of: session.currentPath)` covers this — `activateTab` calls `navigate(to:)` which updates `currentPath`. Verified by inspecting `PaneSession.activateTab` (line 62). Add T4 to lock this in. |
| R6 | `OperationDescriptor` initializer signature doesn't match the call site. | low | Check `Sources/Core/Types/OperationDescriptor.swift` before writing; existing callers in `Sources/FileSystem/Local/LocalFileOperations.swift` are the reference. |
| R7 | Trash MenuItem disabled state evaluation triggers `provider.execute` at view-build time. | low | `Button` action closure isn't invoked until the user clicks; `Task { … }` only runs on tap. Safe. |
| R8 | Non-local file `Open` action lacks a meaningful target. | low | Mark the item disabled when `item.kind != .directory && item.path.scheme != .local`. |

### New tests

Five tests appended to `MainWindowTests.swift` under a new
`// MARK: - FileBrowserView` section:

| # | Test name | Assertion |
|---|---|---|
| T1 | `testFileBrowserSingleTapDoesNotNavigate` | Set up a session at `/Users/test`, seed a directory at `/Users/test/sub`. Construct `FileBrowserView(session:)`. Drive the single-tap path by setting `view.selectedItemPath = path` (or by calling a small testable hook). Assert `session.currentPath == /Users/test`. |
| T2 | `testFileBrowserDoubleTapNavigatesToDirectory` | Same setup; call `session.navigate(to: dirPath)` directly (this is what double-tap does for directories). Assert `session.currentPath == dirPath`. The test verifies the navigation API contract; the gesture wiring itself is implicit. |
| T3 | `testFileBrowserDoubleTapOnFileDoesNotNavigate` | Seed a file item; assert that *not calling* `navigate` (i.e., the file branch) leaves `currentPath` unchanged. Acts as a guard on the `if item.kind == .directory` branching. |
| T4 | `testFileBrowserSelectionClearsOnNavigation` | Hard to reach `@State` directly; instead, verify the contract: after `session.navigate(to:)`, `currentPath` changes — and the view's `.onChange(of: session.currentPath)` will fire on next render. Assert just the `currentPath` change here; document that selection-clearing is exercised by T5's render. |
| T5 | `testFileBrowserViewComposesWithContextMenu` | Build `NSHostingView(rootView: FileBrowserView(session: makeTestPaneSession()))`. Assert non-nil. Forces the compiler to honor the new `.contextMenu` modifier and the gesture chain — same pattern as the existing `testMainWindowViewComposesWithoutCrashing`. |

**Honesty note on T1/T2/T3/T4:** SwiftUI does not expose a way to
synthesize tap events from XCTest without a hosted scene. The tests
above verify the *underlying contract* (the `session.navigate` API)
and a render-time smoke test — they do **not** simulate a real
mouse click. This matches the S01 handoff's wording ("driving the
single-tap closure") and is consistent with how
`testMainWindowViewComposesWithoutCrashing` is written today. If
deeper gesture coverage is wanted later, it would need
`ViewInspector` — out of scope for S02.
