## 2. Design decisions and rationale

### D1. Direct `session.provider.execute(...)` for Trash, NOT closure injection
The S01 handoff recommended threading an `onTrash` closure through
`MainWindowView → PaneHost → FileBrowserView` to route trash through
`MainWindowModel.operationQueue`. The S02 prompt overrides this with the
simpler "call `session.provider` trash operation if available; otherwise
show disabled" — so we call `provider.execute(_:progress:)` directly from
the menu action wrapped in a fire-and-forget `Task`.

- **Pro:** No plumbing changes outside `FileBrowserView`. Smallest possible diff.
- **Con:** Trash will not appear in the transfers panel for now. Acceptable
  per the S02 prompt; revisit in a future session if visibility is wanted.
- **Disabled-when:** `item.path.scheme != .local` (only `LocalFileOperations`
  implements `.trash`; `InMemoryFileSystemProvider` accepts it but is fake).

### D2. Promote `FileBrowserView` to `internal`, add two `internal` tap helpers
`@State private var selectedItemPath` lives inside `FileBrowserView` (per
explicit S02 task #5). Inline gesture closures are not reachable from
XCTest. Two reach options:

- (a) Promote view to `internal` and expose tap *methods* the gestures call.
- (b) Extract a separate `@MainActor FileBrowserModel` type.

Choosing (a) — minimum code, matches the handoff's recommendation, and
keeps the view's state surface as `selectedItemPath` + `items` only.
The two methods are pure side-effect dispatchers:

```swift
internal struct FileBrowserView: View {
    @Bindable var session: PaneSession
    @State private var selectedItemPath: FilePath?
    @State private var items: [FileItem] = []
    @State private var isLoading = true
    @State private var errorMessage: String?
    @Environment(\.theme) private var theme

    func performSingleTap(on item: FileItem) {
        self.selectedItemPath = item.path
    }

    func performDoubleTap(on item: FileItem) {
        if item.kind == .directory {
            self.session.navigate(to: item.path)
        } else if item.path.scheme == .local {
            NSWorkspace.shared.open(URL(fileURLWithPath: item.path.posixString))
        }
    }
    // ...
}
```

Tests assert *negative* behavior (single-tap → `currentPath` unchanged) and
*positive* behavior (double-tap on directory → `currentPath == item.path`).
We do not assert the `@State` selection mutation directly — `@State` is not
durably readable outside a render context. The behavior we care about for
bug-050 is "single tap does not navigate", which is fully testable.

### D3. Modifier order — double-tap declared *before* single-tap
SwiftUI hard requirement; reversing causes single-tap to consume the gesture
and double-tap never fires. Encoded directly in PaneHost.swift line ordering
and called out in a one-line code comment because it is non-obvious WHY
(see Comments policy below).

### D4. `.contextMenu` attached *after* both `.onTapGesture` modifiers
Right-click and left-click are independent mouse buttons in AppKit;
attachment order does not matter for correctness, but placing
`.contextMenu` last keeps the gesture stack visually grouped.

### D5. Selection clears on `session.currentPath` change
`.onChange(of: self.session.currentPath) { _, _ in self.selectedItemPath = nil }`
attached to the `List`. This covers external navigation triggers (toolbar,
sidebar, ⌘[, double-tap) so the highlight does not survive into the new
listing.

### D6. Selection highlight = `theme.colors.accent.opacity(0.15)` on row background
Per S02 task #7. Apply via `.background(self.rowBackground(for: item))`
helper that returns `Color.clear` when not selected. Avoids inline
ternary noise in `body`.

### D7. Menu spec — minimum viable per S02 task #2
| # | Label | Action | Disabled when |
|---|---|---|---|
| 1 | **Open** | `if item.kind == .directory { session.navigate(to: item.path) }` | `item.kind != .directory` (file → disabled per S02 prompt; `NSWorkspace.open` fallback is reserved for double-tap only) |
| 2 | **Move to Trash** | `Task { try? await session.provider.execute(OperationDescriptor(kind: .trash, sources: [item.path]), progress: nil) }` | `item.path.scheme != .local` |
| 3 | **Reveal in Finder** | `NSWorkspace.shared.activateFileViewerSelecting([URL(fileURLWithPath: item.path.posixString)])` | `item.path.scheme != .local` |

Items remain visible — apply `.disabled(...)` rather than omitting from the
menu, per S02 task #4.

### D8. Comments — silence by default; document only the SwiftUI gotcha
Per `CLAUDE.md`: no comments unless the WHY is non-obvious. Two comments
warranted in this diff:
- One above the `.onTapGesture(count: 2)` line: `// Double-tap MUST be declared before single-tap so SwiftUI gives it priority.`
- None on the helper methods, the menu items, the selection background, or the `.onChange`.

### D9. Logger / `print` policy — N/A
No new logging needed. `os.Logger` would only matter if we caught the
`provider.execute` error; we intentionally fire-and-forget with `try?` for
MVP. If the provider rejects the trash op (e.g. read-only volume), the user
will notice the file did not disappear; surfacing that error is out of
scope for this session.

### D10. `Sendable` / Swift 6 strict concurrency
- `FileBrowserView` is a struct (already `Sendable` by composition) on `@MainActor` SwiftUI views.
- `OperationDescriptor`, `FilePath`, `FileItem` are all `Sendable`.
- The `Task { try? await session.provider.execute(...) }` capture is on the main actor; `provider` is `Sendable` (protocol requires it). No `@unchecked Sendable` needed.
- `NSWorkspace.shared.open(_:)` and `.activateFileViewerSelecting(_:)` are AppKit main-thread APIs called from a `@MainActor` view — fine.

## 3. Risks and mitigations

| # | Risk | Likelihood | Mitigation |
|---|---|---|---|
| R1 | Outer `PaneHost.onTapGesture { onActivate }` (line 43) swallows row taps | low | `.onTapGesture` on a child view fires *first*; outer one bubbles. Verify by manual sanity render in T3 (`NSHostingView` smoke). If broken, switch outer to `.simultaneousGesture(TapGesture().onEnded { … })` — ~3-line change. |
| R2 | Single/double-tap gesture priority inverted by accident during edit | medium | Hard rule: declare `count: 2` first. Code comment on that line. Manual verification in handoff verification step (paste console output of a quick run if affordable). |
| R3 | Calling `NSWorkspace.shared.open` from a CI/XCTest run actually launches an app | medium | Tests only ever call `performDoubleTap` on a `.directory` item, never a file. Audit the test list before committing. |
| R4 | `FileBrowserView` requires `@Environment(\.theme)` — smoke test crashes without it | low | Existing `testMainWindowViewComposesWithoutCrashing` already builds an `NSHostingView(rootView: MainWindowView(...))` without setting theme; it relies on the default value path. T3 mirrors that pattern. If it crashes, wrap with `.environment(\.theme, .defaultLight)` (or whatever the design system exports). |
| R5 | `swiftformat --lint` rejects new modifier order or trailing-closure form | low | Run `swiftformat Sources/UI/MainWindow Tests/UITests/MainWindowTests` (no `--lint`) locally first to auto-format, then re-run with `--lint` to confirm zero diff. |
| R6 | `swiftlint --strict` flags the `Task { … }` fire-and-forget as `unused_closure_parameter` or similar | low | The closure has no parameters; no warnings expected. If `discarded_notification_center_observer` analogue fires, append `_ =` or convert to a named function. |
| R7 | `swift build -warnings-as-errors` fails because promoting `private → internal` exposes a previously-implicit type that is itself `private` | low | `FileBrowserView` only references `Spacing`, `FileKindIcon`, `theme`, `PaneSession`, `FileItem`, `ByteCountFormatter`, `Task`, `URL`, `NSWorkspace` — all already `public` or `internal`. No transitive promotion needed. |
| R8 | `provider.execute(_:progress:)` requires the second argument; passing `nil` is allowed | none | Confirmed in `FileSystemProvider.swift:22` (`progress: (any OperationProgressReporting)?`). |
| R9 | Trash menu item disabled-state computed at menu-render time uses captured stale `item` | none | `@ViewBuilder` re-evaluates per item; `.disabled(item.path.scheme != .local)` is recomputed correctly. |
| R10 | Selection-clear `.onChange(of:)` requires `iOS 17`-style two-arg closure on macOS 14 | none | The macOS 14.0 deployment target supports the new `onChange(of:_:)` two-parameter form; matches existing usage in this file (none yet, but standard across the codebase). |

No defects spotted outside `touches:` scope while reading the source.

// MARK: - FileBrowserView (bug-049 + bug-050)

func testFileBrowserSingleTapDoesNotNavigate() {
    let session = makeTestPaneSession()
    let originalPath = session.currentPath
    let view = FileBrowserView(session: session)
    let dir = FileItem(
        path: FilePath(scheme: .local, posix: "/Users/test/Subdir"),

    view.performSingleTap(on: dir)

    let session = makeTestPaneSession()

    let dir = FileItem(path: dirPath, kind: .directory)
    view.performDoubleTap(on: dir)
    XCTAssertEqual(session.currentPath, dirPath)
}

func testFileBrowserViewComposesWithContextMenu() {
    let session = makeTestPaneSession()
    let view = FileBrowserView(session: session)
    let host = NSHostingView(rootView: view)
    XCTAssertNotNil(host)
}

## 6. What this plan deliberately does NOT do

- Does not plumb `onTrash` through `MainWindowView → PaneHost → FileBrowserView`. Direct `provider.execute` per S02 prompt.
- Does not add Copy / Rename placeholder menu items. S02 prompt specifies only Open / Move to Trash / Reveal in Finder; extras are scope creep.
- Does not extract a `FileBrowserModel` type. View has only two pieces of state; a model adds code without payoff.
- Does not refactor the `List(...)` into `List(selection:)`. S01 handoff explicitly warns against this (double highlights / focus rings).
- Does not add an `os.Logger` for trash failures. Out of scope; can be added in a follow-up if users report silent failures.
- Does not introduce CI changes. Session 03 (`session-03-ci-gate.md`) handles CI.
- Does not touch `MainWindowTestSupport.swift` (read-only per session prompt).
- Does not introduce SwiftUI environment defaults or new `.theme()` modifiers; relies on the same path the existing `MainWindowView` smoke test already proves works.
