## Design Decisions and Rationale

### Width: 130 pt

`Text(date, style: .date)` renders using the user's locale-default **long-style** date format, not the short style for which `90` pt was chosen. Measurements:

- `en_US` long style: `"December 31, 2025"` → ~17 chars at caption font ≈ 118 pt
- `de_DE` long style: `"31. Dezember 2025"` → ~18 chars at caption font ≈ 124 pt
- `fr_FR` long style: `"31 décembre 2025"` → ~16 chars ≈ 116 pt

`130` pt provides a comfortable margin over the worst-case `de_DE` rendering and aligns with the prior session-01 audit recommendation. Going higher (e.g., 160 pt) would compress the flexible name column unnecessarily.

### Modifier order: `.lineLimit(1)` before `.frame(...)`

`.lineLimit(1)` constrains the `Text` view's ideal intrinsic size to a single line **before** the frame clamps it. This ensures:
1. SwiftUI does not allocate two-line height for the row.
2. The `frame` modifier sees a single-line text and applies `alignment: .trailing` without producing a two-line layout.

If `.frame` were applied first, the text could still wrap within the frame and only then be truncated — producing an incorrectly tall row for one layout pass before settling.

### Bug #060: No separate fix needed

Session-01 audit established that both panes share the same `LocalFileSystemProvider` instance and identical `enumerate(at:options: .default)` calls (`App/Stevedore/AppEnvironment.swift:50–51`). There is no per-pane divergence in attribute fetching. The "right pane has no dates" symptom is a rendering artifact: at `90` pt with no `.lineLimit`, the date `Text` wraps to two lines in the narrower pane, visually eclipsing the date below the row baseline. The `130` + `.lineLimit(1)` fix resolves both bugs with one edit.

Fallback escalation (diagnostic logging + `URLResourceMapper` audit) applies only if the symptom persists after this fix is applied and verified in session 03 manual testing.
