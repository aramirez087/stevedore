## Design decisions and rationale

### D1. Treat Session 01 as a discovery + paper-design step only

The charter explicitly forbids code changes; the handoff must enable Session 02
(model: sonnet) to apply mechanical edits. The handoff therefore must contain:
- exact file paths
- exact line numbers
- proposed diffs (before/after snippets)
- root-cause statement for each bug
- a fix-or-skip verdict for #061 with cited evidence

### D2. Use the macOS 26 SDK rule from operator rules to verdict #061

Operator rules state:
> `.focusedSceneValue` (emitter) + `@FocusedValue` (reader) is the correct
> scene-proxy pattern on macOS 26 SDK.

Pre-read evidence already confirms:
- `PaneHost.swift:50` — emitter uses `.focusedSceneValue(\.paneCommandProxy, …)` ✅
- `GoMenu.swift:5` — reader uses `@FocusedValue(\.paneCommandProxy)` ✅
- `PaneCommandProxy.swift:127` — `FocusedValues` entry declared with `@Entry`

Verdict in handoff: **bug #061 is already fixed**. No edits in Session 02 for #061.
The handoff must justify the verdict by citing the two line numbers above and the
operator-rules constraint, so Session 03's CI gate can confirm without re-litigating.

### D3. Bug #059 — date column wraps

Pre-read evidence at `PaneHost.swift:224–228`:

```swift
if let date = item.attributes.modificationDate {
    Text(date, style: .date)
        .font(self.theme.typography.caption)
        .foregroundStyle(self.theme.colors.textSecondary)
        .frame(width: 90, alignment: .trailing)
}
```

Findings to record in handoff:
- Frame width is `90` pt — narrower than required for "December 31, 2025" at caption font.
- `.lineLimit(1)` is **absent** — text can wrap.
- Session 02 charter prescribes `~130 pt`; the handoff should request width `130` and
  insertion of `.lineLimit(1)` immediately after `.foregroundStyle(...)` on this Text.

Proposed diff to embed in handoff (before/after at lines 224–229):

```diff
 if let date = item.attributes.modificationDate {
     Text(date, style: .date)
         .font(self.theme.typography.caption)
         .foregroundStyle(self.theme.colors.textSecondary)
-        .frame(width: 90, alignment: .trailing)
+        .lineLimit(1)
+        .frame(width: 130, alignment: .trailing)
 }
```

(Order: `.lineLimit(1)` before `.frame` so the Text reports a single-line ideal size to
the parent layout; placing `.frame` last fixes the column width.)

### D4. Bug #060 — right pane no dates

Pre-read evidence:
- `AppEnvironment.swift:26, 50–51` — both panes are constructed with the **same**
  `localProvider` instance and the **same** `home` initial path.
- `PaneSession` exposes a single shared provider; no per-pane provider configuration.
- `FileBrowserView.loadItems()` (`PaneHost.swift:293–314`) is identical for both panes;
  enumeration uses `.default` options for both.

Therefore the dates returned by `provider.enumerate(...)` cannot legitimately differ
between left and right panes for the same path. The hypothesis to record in the handoff:

> The reported "right pane has no dates" symptom is most likely a **rendering side-effect
> of bug #059**. With the date column at width `90` and no `.lineLimit(1)`, in a
> narrow-right-pane split (DualPaneLayout default = 0.5; user-resized splits routinely
> leave the right pane <400 pt), the wrapped two-line date inflates row height and is
> visually clipped/eclipsed by the row baseline, producing the appearance of "no dates".
> The HStack budget is roughly: icon (~20) + name (flex) + Spacer + size (80) + date (90)
> + Spacing.sm × 4. When the right pane is narrow, the name takes priority and the date's
> 90 pt frame triggers wrap, not omission.

Recommendation in the handoff: **the bug #059 fix (width 130 + `.lineLimit(1)`) is
expected to also resolve bug #060**. The handoff should:

1. State the unified-fix hypothesis explicitly.
2. Mark bug #060 root cause as "shared with #059, no separate code change planned".
3. Add a fallback paragraph: if Session 03 CI gate observes that the right pane still
   lacks dates after the #059 fix is applied, escalate to a follow-up session that:
   - logs `item.attributes.modificationDate` per item from `loadItems()`
   - audits `LocalFileSystemProvider.enumerate` for the attribute set requested under
     `.default` enumeration options
   - inspects whether there is any `.task(id:)` re-entrancy that overwrites `items`
     mid-load (current code uses `await … sorted`, then assigns once — no obvious race
     observed during pre-read).

This decision avoids speculative provider edits in Session 02 (which is `touches`-scoped
to `PaneHost.swift` and `GoMenu.swift` only — provider files are not in scope and
Session 02 charter would need to be amended to touch them).
